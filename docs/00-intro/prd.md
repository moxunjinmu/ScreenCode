## 一、产品概述

### 1.1 产品定位

ScreenCode 是一个 Electron 桌面应用，用于**隔离网络环境下的屏幕捕获和代码提取**。

**核心场景**：外包开发者在内网机器上编写代码，通过采集卡将内网屏幕画面传输到外网个人电脑，ScreenCode 捕获画面后使用多供应商 AI API（智谱 GLM-5、Claude Sonnet 等）进行代码识别和提取，支持多轮 AI 对话和会话管理。

### 1.2 目标用户

在物理隔离网络环境下工作的外包开发者，需要将内网屏幕上的代码快速还原为可编辑文本。

### 1.3 核心价值主张

- **快速提取**：热键截图 → AI 识别 → 代码输出，端到端延迟 < 20s
- **多供应商支持**：4 个 AI 供应商自动路由（Anthropic、智谱标准/Anthropic 兼容、OpenRouter）
- **心流保护**：全局热键操作，Toast 通知，系统托盘常驻
- **会话管理**：多会话并行，标题自动生成，内存存储

## 三、技术架构

### 3.1 技术栈

| 层次 | 技术选型 | 用途 |
|------|----------|------|
| 运行时 | Electron ^28 | 桌面应用框架 |
| 构建 | Electron Forge + Vite | 开发与打包 |
| 前端 | React 18 + TypeScript | UI 框架 |
| 状态管理 | Zustand | 5 个独立 Store |
| 样式 | TailwindCSS | 原子化 CSS |
| 图像处理 | Sharp | 高性能压缩 |
| AI SDK | @anthropic-ai/sdk + openai | 双 SDK 自动路由 |
| 配置存储 | electron-store | 持久化配置 |

### 3.2 进程模型

```
┌─────────────────────────────────────────┐
│         Electron Application            │
├─────────────────────────────────────────┤
│  Main Process (src/main/)               │
│  - Capture: 浏览器预览 + FFmpeg YUY2 单帧│
│  - Processor: RingBuffer/FrameDiff/Sharp│
│  - AI: 服务路由 + Claude/OpenAI 封装      │
│  - Config: electron-store + IPC 推送     │
│  - Tray: 系统托盘                        │
├─────────────────── IPC ─────────────────┤
│  Renderer Process (src/renderer/)       │
│  - React 18 + Zustand + TailwindCSS     │
│  - Store: capture/frame/app/chat/ui     │
│  - Components: Preview/ChatPanel/...    │
├─────────────────────────────────────────┤
│  Preload (src/preload/)                 │
│  - contextBridge 安全隔离               │
└─────────────────────────────────────────┘
```

### 3.3 AI 服务路由

`isOpenAICompatible(baseUrl)` 根据 baseUrl 自动选择 SDK：

| Base URL 匹配 | 使用 SDK | 供应商 |
|--------------|----------|--------|
| `/api/anthropic` | Anthropic SDK | zhipu-anthropic |
| `bigmodel.cn` | OpenAI SDK | zhipu (标准端点) |
| `openrouter.ai` | OpenAI SDK | openrouter |
| 其他 | Anthropic SDK | anthropic (默认) |

### 3.4 多供应商配置

支持 4 个 API 供应商，独立配置：

| ID | 名称 | Base URL | SDK |
|----|------|----------|-----|
| `anthropic` | Anthropic 官方 | api.anthropic.com | Anthropic |
| `zhipu` | 智谱 AI 标准 | open.bigmodel.cn/api/paas/v4 | OpenAI |
| `zhipu-anthropic` | 智谱 Anthropic 兼容 | open.bigmodel.cn/api/anthropic | Anthropic |
| `openrouter` | OpenRouter | openrouter.ai/api/v1 | OpenAI |

### 采集卡最高质量模式协商 ✅（2026-08-28）

用户故事：作为使用 UVC 采集卡的用户，我希望应用优先获得采集卡能够稳定输出的最高分辨率画面，
并明确显示实际生效的分辨率与帧率，避免把预览缩放误认为采集质量提升。

实施范围：

- [x] 复用现有 `captureStore` 与浏览器原生 Media Capture/WebRTC 管线，不引入重复的视频播放器依赖
- [x] 按“最高分辨率优先，同分辨率下最高帧率优先”探测常见采集模式
- [x] 对候选模式使用严格尺寸约束；支持时禁止浏览器裁剪缩放，失败时按候选顺序安全降级
- [x] 使用 `MediaStreamTrack.getSettings()` 与视频元素固有尺寸记录实际生效参数
- [x] 在预览工具栏展示实际采集分辨率和帧率，将采集质量与 CSS 显示缩放明确分离
- [x] 保留现有源分辨率截图、区域截图、全屏预览、设备切换和全局热键行为

本阶段不包含：FFmpeg/GStreamer 原生采集管线、采集卡厂商专有 SDK、HDR/10-bit、
像素格式手动选择，以及修改 AI 图片压缩策略。

验收标准：

1. 连接支持多档输出的采集卡后，应用按既定顺序选择最高可用分辨率；相同分辨率优先较高帧率。
2. 某个严格模式不受设备或驱动支持时，应用继续尝试下一档，不因单次约束失败中断预览。
3. 工具栏展示的是 `getSettings()` 返回的实际宽、高、帧率，不以请求值或 CSS 尺寸冒充实际采集参数。
4. 截图 Canvas 尺寸继续等于视频源固有尺寸，不随预览分辨率或缩放选项改变。
5. 新增模式排序、约束构造和回退逻辑具备自动化测试；typecheck、lint、测试和打包全部通过。

阶段验收记录（2026-08-28）：`npm run test:coverage` 通过 10 个用例，新增协商模块语句覆盖率
93.93%、分支覆盖率 86.53%；`npm run typecheck` 与 `npm run lint` 通过。关闭占用旧输出目录的应用后，
`npm run package` 完整通过，产物为 `out/ScreenCode-1.1.1-20260828-win32-x64`。启动该产物并连接
已保存的 USB Video 采集卡，应用进入“采集中”状态，工具栏显示实际协商结果为
`1920×1080 @ 60 FPS`；随后使用 `Ctrl+Shift+S` 成功将当前帧加入队列（`1/8`），证明源视频截图与
全局热键链路可用。当前驱动与输入信号下的最高质量模式协商、实际参数展示和预览链路通过实机验收。

### 最高有效画质、YUY2 截图与 AI 画质档位 ✅（2026-08-28）

实测纠偏：USB Video（VID `534D` / PID `2109`）在 MJPEG `1920×1080@60` 档位下约 50% 为
4 字节空包，10 秒仅得到约 30 张/秒有效 JPEG；MJPEG `1920×1080@30` 无空包，真实有效帧率
30.001 FPS，当前画面下有效载荷约 35.79 Mbps。因此“最高标称帧率”不等于“最高有效画质”。

用户故事：作为以代码和文字清晰度为首要目标的用户，我希望默认预览选择最高分辨率下稳定、无空包的
有效帧率；截图时临时使用采集卡无压缩 YUY2 模式获得最高单帧保真，并可按任务成本调节发送给 AI 的
图片质量，默认保留原图无损质量。

固定产品策略：

- [x] 默认预览为“画质优先”：分辨率优先，同分辨率优先 `30/29.97 FPS`，保留“流畅优先”可选策略
- [x] 工具栏同时展示轨道配置 FPS 与视频元素实测有效 FPS，避免把标称值当作真实帧率
- [x] 默认截图为“最高保真”：释放 Chromium 视频轨道后，由 FFmpeg DirectShow 使用
      `1920×1080 / YUY2 4:2:2 / 5 FPS` 抓取一帧并编码为无损 PNG，再恢复 MJPEG30 预览
- [x] YUY2 截图失败或 FFmpeg 不可用时必须恢复预览并明确提示；允许回退到当前预览帧但不得静默降级
- [x] FFmpeg 通过无 Shell 参数数组调用；设备名必须来自当前已枚举设备并校验长度与控制字符；设置
      超时、stdout 大小和 PNG 签名上限，异常路径不得残留子进程或锁住采集卡
- [x] `Frame`、聊天附件、缩略图、全屏预览、剪贴板和 AI 服务完整携带 MIME 类型，不再硬编码 JPEG
- [x] Windows 完整打包产物同时解包 Sharp 原生 `.node` 与依赖 DLL，确保 AI 画质处理可启动

AI 图片画质可调且默认最高：

| 档位 | 处理策略 | 默认 |
|------|----------|------|
| 节省 | 最大宽度 768px，JPEG 85，4:4:4 | 否 |
| 平衡 | 最大宽度 1280px，JPEG 90，4:4:4 | 否 |
| 高画质 | 最大宽度 1920px，JPEG 95，4:4:4 | 否 |
| 原图无损 | 不缩放、不重新编码，PNG/JPEG 原样发送 | 是 |

状态与恢复约束：

1. 截图状态依次为 `previewing → pausing → yuy2_capturing → restoring → previewing`。
2. 任一步失败都必须进入 `restoring`；恢复失败需显示独立错误，不能把截图成功等同于预览恢复成功。
3. YUY2 原图仅在内存和 IPC 中传递，不写入项目目录或持久化临时截图文件。
4. 未配置 FFmpeg 或设备不支持 YUY2 时，应用仍可使用 MJPEG 预览和预览帧截图。
5. AI 画质档位只处理发送副本，不改变帧队列和剪贴板中的 YUY2/PNG 原图。

本阶段不包含：把 GPL FFmpeg 二进制打入安装包、HDR/10-bit、厂商 SDK、长期录像，以及修改模型
Prompt 或代码提取业务规则。FFmpeg 作为外部成熟运行时自动发现，并支持配置显式路径。

验收标准：

1. 默认启动 USB Video 后轨道配置为 `1920×1080@30`，2 秒实测有效帧率不低于 29 FPS。
2. `Ctrl+Shift+S` 和截图按钮默认得到 `image/png`、`1920×1080` 的 YUY2 来源帧；预览在 5 秒内恢复。
3. FFmpeg 缺失、超时、设备占用、输出超限和非法 PNG 均有测试，且所有路径都会恢复预览。
4. 四档 AI 图片质量可在设置页保存并即时生效；默认“原图无损”，供应商收到正确 MIME 类型。
5. 自动化测试新增模块覆盖率不低于 80%；typecheck、lint、测试和完整打包全部通过。
6. 实机复验 MJPEG30 无空包、YUY2 PNG 可入队/复制、AI 原图请求可构建，现有区域截图和快捷键不回归。

### YUY2 区域截图与分档输出 ✅（2026-08-28）

用户故事：作为通过采集卡识别代码和文字的用户，我希望区域截图与整帧截图使用同一条高保真采集
链路；默认从 YUY2 全帧裁剪无损 PNG，并可用现有四档画质控制最终截图和 AI 图片输出。

产品策略：

- [x] 进入区域截图时先抓取并冻结一张 YUY2 `1920×1080` 全帧 PNG，选区和最终裁剪基于同一帧
- [x] 默认“最高画质（原图无损）”：YUY2 全帧经源像素裁剪后输出 PNG，不经过 JPEG
- [x] 高画质输出最大宽度 1920px、JPEG 95、4:4:4；平衡为 1280px/JPEG 90；节省为 768px/JPEG 85
- [x] 复用现有四档画质配置，设置页文案明确为“截图与发送给 AI 的图片质量”
- [x] YUY2 不可用时使用已冻结的预览 JPEG 并显示降级原因，不标记为 YUY2 无损图
- [x] 原始全帧与裁剪图仅通过内存和受控 IPC 传递，不创建临时图片文件

选区交互：

- [x] 选区协议使用源图整数像素坐标，不把 CSS 像素、预览缩放或设备像素比写入裁剪协议
- [x] 正确处理 `object-fit: contain` 留白、窗口尺寸变化、全屏预览和 Windows 显示缩放坐标语义
- [x] 保留八方向缩放与整体拖动，增加源像素 `x/y/宽×高` 实时显示
- [x] 支持方向键移动 1px、`Shift+方向键` 移动 10px、`Enter` 保存、`Esc` 取消和 `R` 复用上次区域
- [x] 最小选区、移动、缩放和主进程裁剪均做边界收敛；非法、越界、空区域请求全部拒绝

技术路线：继续复用现有 React 选区层、`captureStore`、FFmpeg YUY2 管线和 Sharp 图像处理，不引入
完整桌面截图引擎。ShareX、Flameshot、Greenshot 仅作为交互参考，不复制 GPL 实现；Snipaste 仅作
闭源产品体验参考。箭头、文字、画笔、马赛克、撤销/重做和贴图属于下一阶段，不混入本阶段。

验收标准：

1. 默认区域截图进入时冻结 YUY2 PNG；确认后队列和剪贴板得到 `image/png` 的源像素裁剪结果。
2. 四档输出的 MIME、最大宽度、JPEG 质量和 4:4:4 策略与设置一致，小选区不放大。
3. 相同画质档位的图片发送给 AI 时不重复编码；切换更低档后允许继续压缩。
4. 坐标映射覆盖横向/纵向留白、四角、窗口 resize、全屏和边界取整，框选内容不缺边、不越界。

## 七、风险与约束

### 7.1 技术风险

1. **视频采集未实现**：当前使用硬编码数据，需实现真实的 desktopCapturer API
2. **帧差分算法简化**：当前返回模拟值，需实现像素级对比算法

### 7.2 合规注意事项

> ⚠️ **重要提示**：本产品涉及屏幕内容采集和云端 AI API 调用，在金融、政府等敏感行业使用时需注意：
>
> 1. **数据出境风险**：调用云端 API 可能将屏幕内容传输至境外服务器
> 2. **敏感信息保护**：请勿截取含个人隐私、商业机密、密钥等敏感信息的画面
> 3. **机构政策合规**：使用前请确认符合所在机构的信息安全政策

### 7.3 使用约束

- Ring Buffer 最大容量：8 帧
- 帧差分阈值：5%（可在配置中调整）
- 聊天图片上限：4 张/消息
- AI API 超时：25 秒
