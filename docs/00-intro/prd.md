## 一、产品概述

### 1.1 产品定位

ScreenCode 是一个 Electron 桌面应用，用于**隔离网络环境下的屏幕捕获和代码提取**。

**核心场景**：外包开发者在内网机器上编写代码，通过采集卡将内网屏幕画面传输到外网个人电脑，ScreenCode 捕获画面后使用多供应商 AI API（智谱 GLM-5、Claude Sonnet 等）进行代码识别和提取，支持多轮 AI 对话和会话管理。

### 1.2 目标用户

在物理隔离网络环境下工作的外包开发者，需要将内网屏幕上的代码快速还原为可编辑文本。

### 1.3 核心价值主张

- **快速提取**：热键截图 → AI 识别 → 代码输出，端到端延迟 < 20s
- **多供应商支持**：4 个 AI 供应商自动路由（Anthropic、智谱标准/Anthropic 兼容、OpenRouter）
- **心流保护**：全局热键操作，Toast 通知，系统托盘常驻
- **会话管理**：多会话并行，标题自动生成，内存存储

## 三、技术架构

### 3.1 技术栈

| 层次 | 技术选型 | 用途 |
|------|----------|------|
| 运行时 | Electron ^28 | 桌面应用框架 |
| 构建 | Electron Forge + Vite | 开发与打包 |
| 前端 | React 18 + TypeScript | UI 框架 |
| 状态管理 | Zustand | 5 个独立 Store |
| 样式 | TailwindCSS | 原子化 CSS |
| 图像处理 | Sharp | 高性能压缩 |
| AI SDK | @anthropic-ai/sdk + openai | 双 SDK 自动路由 |
| 配置存储 | electron-store | 持久化配置 |

### 3.2 进程模型

```
┌─────────────────────────────────────────┐
│         Electron Application            │
├─────────────────────────────────────────┤
│  Main Process (src/main/)               │
│  - Capture: 视频采集 (TODO: 真实实现)    │
│  - Processor: RingBuffer/FrameDiff/Sharp│
│  - AI: 服务路由 + Claude/OpenAI 封装      │
│  - Config: electron-store + IPC 推送     │
│  - Tray: 系统托盘                        │
├─────────────────── IPC ─────────────────┤
│  Renderer Process (src/renderer/)       │
│  - React 18 + Zustand + TailwindCSS     │
│  - Store: capture/frame/app/chat/ui     │
│  - Components: Preview/ChatPanel/...    │
├─────────────────────────────────────────┤
│  Preload (src/preload/)                 │
│  - contextBridge 安全隔离               │
└─────────────────────────────────────────┘
```

### 3.3 AI 服务路由

`isOpenAICompatible(baseUrl)` 根据 baseUrl 自动选择 SDK：

| Base URL 匹配 | 使用 SDK | 供应商 |
|--------------|----------|--------|
| `/api/anthropic` | Anthropic SDK | zhipu-anthropic |
| `bigmodel.cn` | OpenAI SDK | zhipu (标准端点) |
| `openrouter.ai` | OpenAI SDK | openrouter |
| 其他 | Anthropic SDK | anthropic (默认) |

### 3.4 多供应商配置

支持 4 个 API 供应商，独立配置：

| ID | 名称 | Base URL | SDK |
|----|------|----------|-----|
| `anthropic` | Anthropic 官方 | api.anthropic.com | Anthropic |
| `zhipu` | 智谱 AI 标准 | open.bigmodel.cn/api/paas/v4 | OpenAI |
| `zhipu-anthropic` | 智谱 Anthropic 兼容 | open.bigmodel.cn/api/anthropic | Anthropic |
| `openrouter` | OpenRouter | openrouter.ai/api/v1 | OpenAI |

### 采集卡最高质量模式协商 🚧（2026-08-28）

用户故事：作为使用 UVC 采集卡的用户，我希望应用优先获得采集卡能够稳定输出的最高分辨率画面，
并明确显示实际生效的分辨率与帧率，避免把预览缩放误认为采集质量提升。

实施范围：

- [ ] 复用现有 `captureStore` 与浏览器原生 Media Capture/WebRTC 管线，不引入重复的视频播放器依赖
- [ ] 按“最高分辨率优先，同分辨率下最高帧率优先”探测常见采集模式
- [ ] 对候选模式使用严格尺寸约束；支持时禁止浏览器裁剪缩放，失败时按候选顺序安全降级
- [ ] 使用 `MediaStreamTrack.getSettings()` 与视频元素固有尺寸记录实际生效参数
- [ ] 在预览工具栏展示实际采集分辨率和帧率，将采集质量与 CSS 显示缩放明确分离
- [ ] 保留现有源分辨率截图、区域截图、全屏预览、设备切换和全局热键行为

本阶段不包含：FFmpeg/GStreamer 原生采集管线、采集卡厂商专有 SDK、HDR/10-bit、
像素格式手动选择，以及修改 AI 图片压缩策略。

验收标准：

1. 连接支持多档输出的采集卡后，应用按既定顺序选择最高可用分辨率；相同分辨率优先较高帧率。
2. 某个严格模式不受设备或驱动支持时，应用继续尝试下一档，不因单次约束失败中断预览。
3. 工具栏展示的是 `getSettings()` 返回的实际宽、高、帧率，不以请求值或 CSS 尺寸冒充实际采集参数。
4. 截图 Canvas 尺寸继续等于视频源固有尺寸，不随预览分辨率或缩放选项改变。
5. 新增模式排序、约束构造和回退逻辑具备自动化测试；typecheck、lint、测试和打包全部通过。

## 七、风险与约束

### 7.1 技术风险

1. **视频采集未实现**：当前使用硬编码数据，需实现真实的 desktopCapturer API
2. **帧差分算法简化**：当前返回模拟值，需实现像素级对比算法

### 7.2 合规注意事项

> ⚠️ **重要提示**：本产品涉及屏幕内容采集和云端 AI API 调用，在金融、政府等敏感行业使用时需注意：
>
> 1. **数据出境风险**：调用云端 API 可能将屏幕内容传输至境外服务器
> 2. **敏感信息保护**：请勿截取含个人隐私、商业机密、密钥等敏感信息的画面
> 3. **机构政策合规**：使用前请确认符合所在机构的信息安全政策

### 7.3 使用约束

- Ring Buffer 最大容量：8 帧
- 帧差分阈值：5%（可在配置中调整）
- 聊天图片上限：4 张/消息
- AI API 超时：25 秒
